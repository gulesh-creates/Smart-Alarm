## Product goal and scope

Build an offline-first Android alarm clock and study timer called **Zenith** (working name) whose visual design follows the prototype: dark obsidian surfaces, lime accent, Home, Timer, Alarms, Progress and Settings. Implement functional alarm scheduling, focus timer, face-down interaction, walk-to-dismiss, accurate progress, persistence and accessible UI. This is a native Android product; the HTML prototype cannot supply reliable closed-app alarms. There is no account, server or cloud sync requirement. Avoid adding one.

Use Kotlin and Jetpack Compose with a maintainable separation of UI, domain logic, persistence and Android platform adapters. Use Room for versioned alarm/session data and DataStore for preferences unless a simpler choice is justified in the README. Set a supported min SDK and current Play-compliant target SDK after checking current official Android/Play documentation. Pin dependencies and provide a Gradle wrapper. Never commit signing keys, credentials or machine-local paths.

## Implementation order

1. **Map the prototype:** Inventory each visible screen and control. Convert the audit findings into implementation tasks. Keep the design recognizable, but remove the fake status bar, prototype bar, sensor simulator, fake step buttons, seeded data and architecture disclosure from release UI. Debug-only simulation may exist behind a build flag.
2. **Define data and rules:** Model Alarm (stable ID, local time, selected weekdays or one-time date, enabled, label, tone, walk challenge and step target), FocusSession (timestamps, planned duration, actual focus time, completion state), and Settings. Document how a one-time alarm retires, how repeats calculate their next occurrence, and how duplicates are handled. Validate all persisted data and migrate schema changes.
3. **Implement real alarms:** On create/edit/enable/disable/delete, cancel the old PendingIntent as needed and schedule exactly the next eligible occurrence using the current Android alarm API best suited to a user-set alarm clock. Recompute and schedule the following occurrence after a ring. Persist before scheduling; make scheduling idempotent. Handle boot, app replacement, local time/timezone changes, permission change and restored data. Never use an in-process timer, WorkManager periodic job or WebView JavaScript as the alarm trigger. Check exact-alarm access before scheduling and show a clear recovery path if unavailable; display an explicit unscheduled/error status rather than presenting a saved alarm as guaranteed to ring. Choose `USE_EXACT_ALARM` versus `SCHEDULE_EXACT_ALARM` according to current Play eligibility; document the decision and permission flow. Do not claim absolute reliability under every OEM battery policy.
4. **Implement ringing UX:** Use a proper alarm notification/channel, lock-screen flow and current full-screen-intent rules. Handle notification permission denial and full-screen-intent denial with the best supported visible fallback. Provide ringing audio with a tested tone choice, looping, audio focus and cleanup; provide vibration when enabled and supported. Distinguish UI sound setting from alarm sound so alarms do not become unexpectedly silent. Ensure navigation, Dismiss and any Snooze action work even after process recreation. Do not add Snooze unless its schedule/state rules are fully implemented. Prevent duplicate ringing and stale intents. Provide a safe, accessible dismissal route when step challenge cannot be completed; do not trap the user behind an unavailable sensor.
5. **Implement walk challenge:** Prefer `TYPE_STEP_DETECTOR` for per-step events and request `ACTIVITY_RECOGNITION` only when the feature needs it. Check sensor availability and permission. Count steps only for the active ring, guard against duplicate events, and reset on a new alarm. Use an explicitly described fallback on devices without a step detector. Do not assume Health Connect or a raw accelerometer is interchangeable with the step detector.
6. **Implement focus timer and flip behavior:** Keep an explicit Ready/Running/Paused/Completed state machine. Persist the active session and monotonic start/end references; derive remaining time from elapsed time rather than decrementing a counter. Restore accurately after UI recreation and process death, with a documented policy for reboot (monotonic clocks reset). Use only the background service/notification model that current Android rules allow and that the actual sensor or user-visible countdown needs; avoid an always-on service by default. Detect face-down/up with suitable native orientation/gravity data, hysteresis and dwell time. Show sensor availability and offer a real manual Start/Pause/Resume path if unavailable or denied. Completion should write exactly one session.
7. **Implement real statistics:** Fresh install must start empty. Compute today, week, month, goals, longest block and recent sessions from stored timestamps in the device's local timezone. The segmented Day/Week/Month tabs must change the dataset, labels and chart. Recompute after midnight/timezone change. Never show sample values in release. Decide whether incomplete sessions count as focus minutes and state that rule in the UI/README.
8. **Finish UX and accessibility:** Preserve the visual style while using Compose semantics, TalkBack labels, scalable type, touch targets, clear error/empty/permission states and proper contrast. Keep all controls reachable on small phones and with large text. Make tones, vibration and all settings effective. Use a single consistent custom timer range in UI and validation. Remove misleading “production guarantee” copy.
9. **Ship a reviewable project:** Update the existing README and `.gitignore`; add prerequisites/build/run/release instructions, architecture and permission rationale, tests, and a concise test report. Keep personal alarm/session data on-device by default, avoid unnecessary permissions and network calls, and document backup/export, privacy policy and Play Data Safety answers based on actual implementation. Build the APK/AAB and run all available automated checks. If real Android hardware or SDK is unavailable, say exactly what was verified locally, mark the real-device cases unverified and do not claim production readiness.

## Required tests

Write focused unit tests for recurrence/next-occurrence calculation (including weekday selection, midnight, DST gap/overlap and timezone change), timer state transitions and drift restoration, statistics day boundaries, persistence migration, and duplicate completion/ring prevention. Add Android integration or instrumentation tests for alarm scheduling/cancellation, boot rescheduling, permission denial/re-grant, notification/ringing lifecycle and sensor fallback where practical. Perform the real-device checks in `PRODUCTION_ACCEPTANCE_CHECKLIST.md`, especially locked screen, Doze and reboot. Record device, Android version, steps and observed result; do not mark unrun cases passed.
